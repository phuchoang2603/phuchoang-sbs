The Problem: Static Kubeconfig Files
#

To perform action on the cluster, you would need kubectl. But have you wonder how kubectl can authenticate and talk to the cluster or the api-server? The answer lies on thekubeconfig file, which is a way for you to specify the IP address of the control plane, how to authenticate to it and grant you access for the kubectl command. Most of people usually get their kubeconfig be fetching from their control plane and call it a day. But as you can see from the commands below, it contain a static certificate credentials inside your kubeconfig. And because you fetch from the control plane, this certificate probably have the full access to your whole cluster. Imagine you lost your laptop or give it to someone else…

Not to mention, when you have multiple people working on the cluster, you would most likely have to restrict the access to the cluster using different policy for each group (admins, developers, and viewers) and environment (dev, staging, prod). Therefore, you can’t distribute this same kubeconfig out to those guys. When something wrong happened, it would be harder to track who perform the changes and track down the root of the problem to solve. And if someone leave the team, how can you make sure that guy can not authenticate to the cluster again ?

To be honest, this problem is similar to how environment secrets and SSH keys reside in my machine in the previous part. When my laptop died, I can no longer connect to my Kubernetes cluster anymore; and because I also lost my SSH private key to authenticate to the control plane, I couldn’t try to get back the access token on the server too. Which means I have to re init and bootstrap the whole cluster from the beginning.

When I tried to migrate my project to using Github Actions and Hashicorp Vault, although I have solve the environment secrets and SSH key problems using Hashicorp Vault secret engine, the problem of authenticate to Kubernetes using kubeconfig is still kinda tricky for me. However, when I finally grasp how OIDC and JWT work with Github Actions and Vault, I got motivated to implement this concept to Kubernetes too.

A little recap on how the runner can authenticate to my Vault server to fetch the secrets from them. Basically, it first try to talk to the OIDC provider (in this case, Github) to get the trusty JWT token from it, then provide it to the Vault server. Next, the Vault server will try to verify this token to the OIDC provider to see if it actually be generated from it. If all the steps is success, the Vault will now trust the runner and let it do whatever it want.

Mapping to the current situation, the runner would be my machine (or kubectl), the target identity we want to authenticate is now the Kubernetes cluster. So, we will likely need a OIDC provider. Researching the internet, I found there are plenty of service to provide this, notably Authentik, Authelia, or Keycloak. This mean I have to deploy another application to my cluster. However, this raise the chicken and egg problem: we want to authenticate to the Kubernetes cluster to deploy it, but we cant because it require OIDC provider and it haven’t been deployed yet. Technically, I could use Ansible to deploy it, but having to wait and debug the service would be so much harder if we couldn’t have kubectl from the beginning.

However, it seems that I have found out Hashicorp Vault, while being the secret management, also happen to be a OIDC provider too.

The Solution: Vault as an OIDC Provider
#

Looking back to how the runner talk to OIDC provider, because those two (runner and OIDC provider) are from the same service (i.e Github), we don’t need to worry about how they can talk together and exchange the trusty JWT token. However in this case, the client (i.e kubectl) and the OIDC provider (Vault) is not from the same service, so we have to config Vault to verify the client before provide it the trusty JWT token.

kubectl plugin for Kubernetes OpenID Connect authentication (kubectl oidc-login)

Go
2108
222

Additionally, kubectl is kinda dumb, it don’t know how to authenticate to Vault and get back the token. Therefore, the repo above was born to assist it. When you execute kubectl, it will opens the browser and you can log in to the provider. Then kubelogin gets a token from the provider and kubectl access Kubernetes APIs with the token. It will store that token to cache, if it valid, kubectl would execute normally, otherwise, it will open the browser to re-authenticate again with the OIDC provider.

Not to mention, using this approach, we also have the capability to grant access based on groups (admin, developer, viewer). When we log in to the OIDC provider on the browser, it will now know who we are (of course, we have to implement how to create group and add the user to them first) and then grant the JWT token with the following field :

  • sub: user email
  • groups: the group that user belong to (admin, developer, viewer)
  • iss and aud: these are critical value. essentially, it is needed for kubernetes api-server to verify the token is came from the Vault, not some random dude making it up.

Finally, when kubectl provide this token to the kubernetes api-server, it will check all the field from the token (we must config the flag to trust the iss and aud when bootstrap the cluster), mapping with the policies (we need to implement RBAC manifest and policies allow what each group can do), and then return the result accordingly. If one of the field does not match, it won’t return anything. If all the field match but the user, for example, are viewer and trying to create deployment files, it will check with the RBAC and denied the actions.

Here’s the general workflow would be:

kubelogin flow (Steps 1-6):

  1. User runs kubectl get nodes
  2. kubectl detects no token/expired → triggers OIDC login
  3. kubelogin opens browser to OIDC issuer and have the user login with username/password (userpass auth)
  4. Vault return ID token + groups claim to kubelogin
  5. kubelogin cache the token locally for further access
  6. kubelogin add token to Authorization header

kubenetes-api-server flow (Steps 7-11):

  1. API request with ID token to Kubernetes API
  2. Verify token with OIDC issuer. If token valid -> extract user + groups
  3. RBAC check, based on the groups claim from the JWT token
  4. Allow/Deny based on RBAC
  5. Return result to user

With that background knowledge and overview, again, let’s jump into the implementation right away.

Step 1: Configure Vault as an OIDC Provider
#

As mentioned before, in our previous part, since the Github Actions runner and OIDC provider are from the same service, we don’t need to config too much. However, in this case, we have to do a lot. And by a lot, we don’t want to mess creating this with the clunky UI on the website. Therefore, terraform to the rescue. And because this is also a one time process, we would do this on terraform-admin, which we also have use for creating JWT auth backend and SSH CA signer for the Vault. This time, we will configure Vault to act as an OIDC provider. This involves creating:

  • A user backend to identify … user (duh). For the sake of simplicity we are going to setup a simple userpass (username/password) backend. But keep in mind that you can also use other backend such as AWS/Azure/GCP auth, TLS certificates authentication as well as LDAP and many more.
  • The Vault entities that map to these users
  • The groups that these entities will belong to and for different access levels
  • An OIDC endpoint so authenticated users may get their OIDC tokens. This also invovles:
    • OIDC scopes to include user metadata in tokens
    • OIDC client for Kubernetes to trust
    • OIDC provider with proper issuer configuration

However, because of my skill issue, we need to create the Vault identity groups, OIDC endpoint first, before creating the user backend. The reason for this is because I had written my Terraform code to reference the group directly

Creating Vault Identity Groups
#

First, we create three groups corresponding to Kubernetes RBAC roles:

File: terraform-admin/modules/vault-oidc-kubernetes/main.tf

# Create Vault groups for Kubernetes RBAC
resource "vault_identity_group" "kubernetes_admins" {
  name     = "${var.env}-kubernetes-admins"
  type     = "internal"
  policies = []

  metadata = {
    environment = var.env
    purpose     = "Kubernetes cluster administrators"
  }
}

resource "vault_identity_group" "kubernetes_developers" {
  name     = "${var.env}-kubernetes-developers"
  type     = "internal"
  policies = []

  metadata = {
    environment = var.env
    purpose     = "Kubernetes application developers"
  }
}

resource "vault_identity_group" "kubernetes_viewers" {
  name     = "${var.env}-kubernetes-viewers"
  type     = "internal"
  policies = []

  metadata = {
    environment = var.env
    purpose     = "Kubernetes read-only viewers"
  }
}

Configuring OIDC Scopes
#

OIDC scopes define what information is included in the JWT token. We need custom scopes for email, profile, and groups:

# Create OIDC key for signing tokens
resource "vault_identity_oidc_key" "kubernetes" {
  name               = "${var.env}-kubernetes"
  allowed_client_ids = ["*"]
  rotation_period    = 3600
  verification_ttl   = 3600
}

# Create custom scope for email
resource "vault_identity_oidc_scope" "email" {
  name        = "${var.env}-email"
  description = "Email scope for ${var.env} Kubernetes"
  template    = <<-EOT
    {
      "email": {{identity.entity.metadata.email}}
    }
  EOT
}

# Create custom scope for profile
resource "vault_identity_oidc_scope" "profile" {
  name        = "${var.env}-profile"
  description = "Profile scope for ${var.env} Kubernetes"
  template    = <<-EOT
    {
      "name": {{identity.entity.name}},
      "preferred_username": {{identity.entity.aliases.${var.userpass_auth_accessor}.name}}
    }
  EOT
}

# Create custom scope for groups
resource "vault_identity_oidc_scope" "groups" {
  name        = "${var.env}-groups"
  description = "Groups scope for ${var.env} Kubernetes"
  template    = <<-EOT
    {
      "groups": {{identity.entity.groups.names}}
    }
  EOT
}

Creating the OIDC Provider and Client
#

# Create OIDC provider
resource "vault_identity_oidc_provider" "kubernetes" {
  name = var.env

  https_enabled = true
  issuer_host   = replace(var.vault_addr, "https://", "")

  allowed_client_ids = [
    vault_identity_oidc_client.kubernetes.client_id
  ]

  scopes_supported = [
    vault_identity_oidc_scope.email.name,
    vault_identity_oidc_scope.profile.name,
    vault_identity_oidc_scope.groups.name,
  ]
}

# Create OIDC assignment (controls who can authenticate)
resource "vault_identity_oidc_assignment" "kubernetes" {
  name = "${var.env}-kubernetes-users"

  group_ids = [
    vault_identity_group.kubernetes_admins.id,
    vault_identity_group.kubernetes_developers.id,
    vault_identity_group.kubernetes_viewers.id,
  ]
}

# Create OIDC client for Kubernetes
resource "vault_identity_oidc_client" "kubernetes" {
  name = "${var.env}-kubernetes"
  key  = vault_identity_oidc_key.kubernetes.name

  redirect_uris = var.redirect_uris

  assignments = [
    vault_identity_oidc_assignment.kubernetes.name
  ]

  id_token_ttl     = 3600 # 1 hour
  access_token_ttl = 3600 # 1 hour

  client_type = "public"
}

# Store OIDC client_id in Vault KV for use by Ansible
resource "vault_generic_secret" "oidc_client_id" {
  path = "kv/${var.env}/oidc"

  data_json = jsonencode({
    client_id = vault_identity_oidc_client.kubernetes.client_id
  })
}

Step 2: Configure Kubernetes API Server for OIDC
#

Now that Vault is configured as an OIDC provider, we need to configure the Kubernetes API server to trust tokens issued by Vault.

Updating RKE2 Server Configuration
#

We add OIDC configuration to the RKE2 server config template:

File: ansible/roles/add_server/templates/rke2-server-config.j2

write-kubeconfig-mode: "0644"
token: {{ rke2_token }}
tls-san:
  - {{ vip }}
{% for host in groups['servers'] %}
  - {{ hostvars[host]['ansible_host'] }}
{% endfor %}
node-label:
  - server=true
disable-cloud-controller: true
disable:
- rke2-ingress-nginx
kube-proxy-arg:
  - "proxy-mode=ipvs"
  - "ipvs-strict-arp=true"
kube-proxy-extra-mount:
- "/lib/modules:/lib/modules:ro"
kube-apiserver-arg:
  - "oidc-issuer-url={{ oidc_issuer_url }}"
  - "oidc-client-id={{ oidc_client_id }}"
  - "oidc-username-claim=preferred_username"
  - "oidc-groups-claim=groups"
  - "oidc-groups-prefix=oidc:"

GitHub Actions: Fetching OIDC Secrets
#

In the GitHub Actions workflow, we fetch the OIDC configuration from Vault:

File: .github/workflows/terraform-ansible.yml (excerpt)

- name: Import Secrets from Vault
  uses: hashicorp/vault-action@v3
  id: vault_auth
  with:
    method: jwt
    url: ${{ vars.VAULT_ADDR }}
    role: ${{ steps.set-role.outputs.role }}
    outputToken: true
    secrets: |
      kv/shared/data/cloudflare * | SSL_ ;
      kv/${{vars.ENV_NAME}}/data/ip * | IP_ ;
      kv/${{vars.ENV_NAME}}/data/rke2 * | RKE2_ ;
      kv/${{vars.ENV_NAME}}/data/oidc client_id | OIDC_CLIENT_ID ;

- name: Set OIDC Issuer URL
  run: |
    echo "OIDC_ISSUER_URL=${{ vars.VAULT_ADDR }}/v1/identity/oidc/provider/${{ vars.ENV_NAME }}" >> $GITHUB_ENV

Step 3: Deploy Kubernetes RBAC Policies
#

With the API server configured for OIDC, we need to create Kubernetes RBAC bindings that map Vault groups to Kubernetes roles.

ClusterRoleBinding for Admins
#

File: ansible/roles/add_server/templates/oidc-rbac-cluster-admin.yaml.j2

---
# Grant cluster-admin to kubernetes-admins group
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: oidc-cluster-admins
  annotations:
    description: "Grants cluster-admin access to kubernetes-admins group"
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: Group
    name: oidc:{{ env }}-kubernetes-admins
    apiGroup: rbac.authorization.k8s.io

ClusterRole and Binding for Developers
#

File: ansible/roles/add_server/templates/oidc-rbac-developer.yaml.j2

---
# Developer role with read/write access to common resources
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: developer
rules:
  # Core resources
  - apiGroups: [""]
    resources:
      [
        "pods",
        "pods/log",
        "pods/exec",
        "services",
        "configmaps",
        "secrets",
        "persistentvolumeclaims",
      ]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Apps
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets", "daemonsets", "replicasets"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Batch jobs
  - apiGroups: ["batch"]
    resources: ["jobs", "cronjobs"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Networking
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses", "networkpolicies"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Autoscaling
  - apiGroups: ["autoscaling"]
    resources: ["horizontalpodautoscalers"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
  # Read-only access to nodes and namespaces
  - apiGroups: [""]
    resources: ["nodes", "namespaces"]
    verbs: ["get", "list", "watch"]
---

Step 4: User Management with Terraform
#

Now we need to create users in Vault and assign them to groups. This is done in terraform-admin.

Creating Users Module
#

File: terraform-admin/modules/vault-user/main.tf

# Create userpass user
resource "vault_generic_endpoint" "user" {
  path                 = "auth/userpass/users/${var.username}"
  ignore_absent_fields = true

  data_json = jsonencode({
    password = var.password
  })
}

# Create entity for the user
resource "vault_identity_entity" "user" {
  name     = var.username
  policies = var.policies

  metadata = {
    email = var.email
  }
}

# Create alias linking userpass auth to entity
resource "vault_identity_entity_alias" "user" {
  name           = var.username
  mount_accessor = var.userpass_auth_accessor
  canonical_id   = vault_identity_entity.user.id
}

# Add user to groups
resource "vault_identity_group_member_entity_ids" "user_groups" {
  for_each = toset(var.group_ids)

  group_id          = each.value
  member_entity_ids = [vault_identity_entity.user.id]
  exclusive         = false
}
